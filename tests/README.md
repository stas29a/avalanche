# Тесты

Сравнение с Redis, Valkey, Memcached, Dragonfly и KeyDB, Docker-стенд и графики:
[comparison/README.md](comparison/README.md).

Локальное сравнение текущего Avalanche с Git-версией без Docker:

```sh
bash tests/comparison/run-local.sh --baseline-ref HEAD
```

Без `--baseline-ref` скрипт сравнивает с сохранённым бинарником последнего
локального прогона; при первом запуске сохраняет текущую версию как baseline.
Обе версии запускаются отдельными процессами и измеряются заново. Параметры:
[local comparison guide](../docs/benchmarks/README.md#local-avalanche-comparison-without-docker).

Обычные тесты:

```sh
cargo test
```

Сетевые проверки используют подставной `CommandExecutor`: он фиксирует вызовы и
возвращает результат, который listener должен отправить клиенту. Проверяются
ошибка исполнителя, продолжение обработки после неё и отмена между командами.
Исполнитель получает `&NetworkFrame<Bytes>`; ответы проверяются непосредственно
в TCP-соединениях, включая порядок и идентификатор запроса.
Интеграционные проверки используют `DefaultCommandExecutor` с общим `Arc<Storage>`
и проверяют TCP-ответы, перезапись между соединениями, пустые значения и бинарные
значения 512 KiB в текущем хранилище Papaya.
Парсер получает `&mut BytesMut`: проверки убеждаются, что неполный кадр не
потребляется, готовый кадр удаляется из буфера, остаток сохраняется, а тело `Bytes`
разделяет исходную память. Тестовый наблюдатель использует Tokio unbounded mpsc.
В текущем `Config` нет `command_worker_count`: команды выполняются
непосредственно в задаче соединения.

Текущий ответ сервера: `[payload_len: i32 BE][request_id: i32 BE][status: i32 BE][payload]`.
Длина относится только к payload; статус проверяется отдельно. Статусы: `0` —
ошибка, `1` — успех, `2` — пустой результат, `3` — значение. Запросы сохраняют
формат `[body_len: i32 BE][request_id: i32 BE][body]`.

Ответ отправляется через `write_vectored`: 12-байтовый заголовок и существующий
payload передаются отдельными срезами без сборки общего буфера. Проверки записи
покрывают частичные записи с backpressure, нулевой прогресс и закрытое соединение.

Нагрузочные тесты находятся в `tests/load.rs` и по умолчанию пропускаются.
Для замера производительности запускайте их в release:

```sh
cargo test --release --test load -- --ignored --nocapture --test-threads=1
```

Отдельные режимы:

```sh
cargo test --release --test load get_rps -- --ignored --nocapture
cargo test --release --test load set_rps -- --ignored --nocapture
cargo test --release --test load mixed_rps -- --ignored --nocapture
```

Каждый тест поднимает `Server` на свободном порту loopback и открывает несколько
постоянных TCP-соединений. GET читает существующие ключи, SET перезаписывает ключи
в ограниченном наборе, смешанный режим чередует GET и SET в пропорции 50/50.
Для каждого числа клиентов создаётся новое хранилище с заранее заполненными
ключами. На одно соединение приходится один незавершённый запрос.

Параметры задаются переменными окружения:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `AVALANCHE_LOAD_CLIENTS` | `1,8,32,128` | Число одновременных клиентов в последовательных замерах |
| `AVALANCHE_LOAD_SECONDS` | `3` | Длительность одного замера в секундах |
| `AVALANCHE_LOAD_WARMUP_SECONDS` | `1` | Прогрев перед каждым замером; `0` отключает прогрев |
| `AVALANCHE_LOAD_VALUE_BYTES` | `256` | Размер значения в байтах |
| `AVALANCHE_LOAD_KEYS` | `1024` | Количество ключей; каждый ключ занимает 8 байт |
| `AVALANCHE_LOAD_WORKERS` | `30` | Устаревший параметр совместимости; при обработке в задаче соединения не влияет на параллелизм |
| `AVALANCHE_LOAD_THREADS` | Число доступных процессоров | Количество рабочих потоков общего Tokio runtime |

Например, более длинный прогон с другим числом клиентов:

```sh
AVALANCHE_LOAD_CLIENTS=16,64,256 \
AVALANCHE_LOAD_SECONDS=10 \
AVALANCHE_LOAD_WARMUP_SECONDS=2 \
AVALANCHE_LOAD_VALUE_BYTES=1024 \
cargo test --release --test load -- --ignored --nocapture --test-threads=1
```

Вывод содержит RPS, число успешно выполненных GET и SET, ошибки и `drained`.
RPS считается как количество полностью полученных и проверенных ответов внутри
окна замера, делённое на длительность этого окна. Проверяются идентификатор
запроса, длина ответа, код результата и возвращённые данные. Соединения,
подготовка данных и прогрев в замер не входят. Ответы на запросы, завершившиеся
после конца окна, дочитываются и учитываются только в `drained`. Таймаут запроса
составляет 5 секунд. При ошибках тест завершается с неуспехом.

`BEST measured RPS` показывает лучший результат среди выбранных уровней нагрузки.
Клиенты и сервер работают в одном процессе, используют общий Tokio runtime;
логирование приложения отключено, используется текущее хранилище Papaya. Результат характеризует
этот локальный прогон. Число клиентов, размер значений, оборудование и включённые
логи влияют на производительность.
