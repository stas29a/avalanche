# Сравнение Avalanche с Redis, Valkey, Memcached, Dragonfly и KeyDB

Для локального сравнения двух версий Avalanche **без Docker**:

```sh
bash tests/comparison/run-local.sh --baseline-ref HEAD
```

По умолчанию текущая версия берётся из рабочего дерева, baseline — из указанной
Git-ревизии. Без `--baseline-ref` используется бинарник последнего успешного
локального прогона; обе версии измеряются заново одним генератором нагрузки.
По умолчанию число потоков сервера равно числу доступных логических процессоров;
`--server-threads N` позволяет задать его явно.
Подробности и параметры: [local comparison guide](../../docs/benchmarks/README.md#local-avalanche-comparison-without-docker).

Сервер `bench-server` и основной бинарник `avalanche` используют общую библиотеку
из `src/lib.rs` и профиль сборки из корневого `Cargo.toml`. Клиент нагрузки и
тесты внешних БД остаются отдельным Cargo-пакетом в `tests/comparison`.
Локальный запуск сохраняет снимок исходников, манифестов и lock-файлов для
воспроизводимости; старые Git-версии собираются с прежней точкой входа.
Для каждой базы в `tests/` есть три Rust-теста: `get_rps`, `set_rps`, `mixed_rps`.
Все используют один генератор нагрузки из `src/lib.rs`. Протоколы:

| База | Протокол |
| --- | --- |
| Avalanche | Текущий бинарный протокол приложения |
| Redis, Valkey, Dragonfly, KeyDB | RESP2 |
| Memcached | Basic text с подтверждением записи |

Для Avalanche клиент перед нагрузкой определяет формат ответа по GET отсутствующего
ключа. Поддерживаются текущий `[payload_len: i32 BE][request_id: i32 BE][status: i32 BE][payload]`
и прежний `[body_len: i32 BE][request_id: i32 BE][status: u8][payload]`, где статус
входил в длину тела. Запросы в обеих версиях одинаковые. Это сохраняет возможность
локального сравнения с прежними Git-версиями; различия протокола входят в результат.
Выбранный формат записывается в лог клиента как `AVALANCHE_RESPONSE_FORMAT=...`.

## Подготовка и полный прогон

Нужны Docker Desktop / Docker Engine с минимум 8 CPU и примерно 8 GiB RAM,
Python 3.12+ и интернет для первоначальной загрузки образов и зависимостей.
На ARM64 используются ARM64-образы, без эмуляции x86. Порты на хост не публикуются.

Из корня репозитория:

```sh
bash tests/comparison/run.sh --build --pull
```

Скрипт создаёт локальное `.venv`, устанавливает зависимости графиков, собирает
образ стенда, загружает базы и выполняет сравнение. Эквивалентные шаги вручную:

```sh
python3 -m venv tests/comparison/.venv
tests/comparison/.venv/bin/python -m pip install -r tests/comparison/requirements.txt
tests/comparison/.venv/bin/python tests/comparison/run.py --build --pull
```

Если образ клиента и образы баз уже подготовлены:

```sh
bash tests/comparison/run.sh
```

Прогон по умолчанию занимает около 10 минут: шесть баз × три режима × четыре
уровня нагрузки × три повтора. После завершения скрипт строит графики и HTML-отчёт.
Для быстрой проверки инфраструктуры и протоколов:

```sh
tests/comparison/.venv/bin/python tests/comparison/run.py --quick
```

Можно выбрать базы, число соединений и более длинные окна:

```sh
tests/comparison/.venv/bin/python tests/comparison/run.py \
  --databases avalanche,redis,valkey,memcached,dragonfly,keydb \
  --clients 1,8,32,128 \
  --seconds 10 --warmup-seconds 2 --repeats 5 \
  --keys 100000 --value-bytes 1024
```

Для сервера с 16 логическими CPU, где CPU `0/8`, `1/9`, …, `7/15` — пары SMT:

```sh
bash tests/comparison/run.sh --build --pull \
  --server-threads 14 --client-threads 2 \
  --server-cpuset 0-6,8-14 --client-cpuset 7,15 \
  --server-memory 8g --database-memory-mib 4096 \
  --network-mode loopback --clients 1,8,32,128,512
```

`--server-threads` задаёт Tokio worker threads Avalanche, worker threads Memcached,
proactor threads Dragonfly, server threads KeyDB и I/O threads Redis/Valkey.
В Redis/Valkey это не означает параллельное выполнение всех команд в 14 потоках.
Квоты CPU контейнеров соответствуют указанным числам потоков. CPU-наборы должны
быть непересекающимися, а число потоков — помещаться в свой набор.
`--server-memory` задаёт лимит серверного контейнера;
`--database-memory-mib` — `maxmemory` остальных баз / `-m` Memcached.
У Avalanche ограничение памяти задаётся контейнером.

В режиме `--network-mode loopback` сервер запускается с `--network none`,
а клиент присоединяется к его сетевому namespace через `--network container:...`.
Соединения идут через `127.0.0.1`; CPU и память учитываются в разных контейнерах.
Сетевые интерфейсы хоста и публикация портов не используются. При сборке в этом
режиме Docker использует host network для скачивания зависимостей.
Режим по умолчанию — `bridge`; его результаты измеряют другой сетевой путь.
Число потоков, лимиты и сетевой режим записываются в metadata и наследуются при `--update`.

`--output /absolute/path/to/new-directory` задаёт каталог результатов;
`--no-plots` выполняет замеры без matplotlib. Для повторного построения графиков:

```sh
tests/comparison/.venv/bin/python tests/comparison/plot.py tests/comparison/results/RUN_DIRECTORY
```

## Перезапустить только Avalanche и обновить сравнение

Из корня репозитория:

```sh
bash tests/comparison/run.sh --databases avalanche --build \
  --update tests/comparison/results/RUN_DIRECTORY
```

`--build` пересобирает Docker-образ из текущих исходников Avalanche. Запускаются
только его проверки и замеры GET/SET/mixed. Параметры нагрузки и CPU автоматически
берутся из `metadata.json` указанного отчёта, чтобы сохранить сопоставимость.
Замеры и сведения о версиях остальных баз сохраняются; графики, таблицы и
`report.html` пересчитываются с новыми результатами Avalanche.

Новый прогон хранится в `RUN_DIRECTORY/updates/TIMESTAMP-ID/`, там же в
`previous/` сохраняются прежние данные, отчёт и заменяемые логи. При ошибке
замера или построения графиков исходный отчёт не обновляется. В `metadata.json`
сохраняются история обновлений и ссылка на отдельный прогон с его версиями,
исходниками и окружением. Даты замеров каждой базы видны в HTML-отчёте.
`--update` требует явного `--databases` и не допускает изменения параметров нагрузки,
а также `--quick` / `--no-plots`.

Для отдельного нового отчёта только по Avalanche, без обновления сравнения:

```sh
bash tests/comparison/run.sh --databases avalanche --build
```

## Что выполняет стенд

1. Создаёт отдельную внутреннюю Docker-сеть с уникальным именем.
2. Поочерёдно запускает по одной базе. Образы закреплены digest в `databases.json`.
3. Выделяет серверу CPU `0-3`, клиенту CPU `4-7`: процессы не делят CPU внутри VM.
   У обоих есть квота 4 CPU. Лимит контейнера сервера — 2 GiB, клиента — 1 GiB.
4. Запускает три настоящих Rust-теста выбранной базы внутри клиентского контейнера.
   Для этой проверки используются два клиента и короткое окно 0.1 секунды.
5. Перед каждой серией проверяет отсутствие ключа, SET/GET бинарного значения
   и перезапись. Затем заполняет весь набор ключей через TCP с подтверждениями.
6. Для каждого режима и числа соединений выполняет прогрев и повторные замеры.
7. Сохраняет сырые данные, настройки, версии, хеши образов и исходников, логи.
8. Удаляет только собственные тестовые контейнеры и сеть, включая аварийный выход.

В качестве серверного окружения используется Docker Linux для всех баз, включая
Avalanche. Корневой `src/bin/bench-server.rs` — тестовая точка запуска общей библиотеки
приложения: число потоков Tokio определяется через `std::thread::available_parallelism()`
или задаётся в `BENCH_SERVER_THREADS`. Команды выполняются в задаче соединения,
используется текущее хранилище приложения, создаваемое через `Storage::new()`.
Логирование каждого запроса не инициализируется.
Эта точка запуска не использует `src/main.rs`, где параметры
сервера фиксированы. Остальные базы настроены на 4 потока обработки/I/O,
если такая настройка поддерживается; это не означает, что все команды каждой
базы исполняются параллельно на четырёх ядрах.

В Docker-профиле серверу доступны четыре выделенных CPU, поэтому автоподбор даст
четыре потока. При прямом локальном запуске сервер использует все доступные ему
логические процессоры. Выбранное число записывается в лог как
`AVALANCHE_SERVER_THREADS=N`.

Рабочее хранилище передаётся в `DefaultCommandExecutor` и `Server` через один
`Arc<Storage>`. В текущем `Config` нет числа обработчиков команд;
команды выполняются в задаче соединения. Результаты
прежней архитектуры с очередью требуют нового замера для сравнения с текущей.

Persistence, репликация, TTL, сжатие на клиенте и TLS не используются. Набор
ключей ограничен, поэтому SET измеряет перезапись существующего ключа, а не
постоянный рост хранилища. Ключи — одинаковые ASCII-строки длиной 8 байт,
значения — одинаковые бинарные данные. GET имеет 100% попаданий. В смешанном
режиме GET/SET чередуются 50/50; выбор ключа псевдослучайный и не связан с
чётностью операции. На соединении не более одного незавершённого запроса.

Dragonfly использует io_uring: для всех серверных и клиентских контейнеров задан
одинаковый `seccomp=unconfined`. Эти контейнеры не получают каталоги хоста или
Docker socket и не публикуют порты. Для сервера также разрешён memlock.
По умолчанию лимит данных остальных баз — 1 GiB; Dragonfly требует минимум такой
объём при четырёх потоках. Для профиля на 14 потоках используется 4 GiB и лимит
контейнера 8 GiB. У Avalanche ограничение памяти задаётся контейнером.

## Метрики и артефакты

- `raw.jsonl`, `raw.csv`: каждый отдельный замер, без усреднения.
- `metadata.json`: версии, архитектура, CPU, память, команды запуска, digest
  образов, SHA256 файлов приложения, результаты отдельных Rust-тестов.
- `summary.csv`: медиана, min/max RPS, медианы p50/p95/p99 при каждом уровне нагрузки.
  Также `ram_avg_bytes_median` — медиана среднего RAM повторов,
  `ram_peak_bytes_max` — максимальный наблюдаемый пик, `ram_repeats` — число повторов с RAM.
- `best.csv`: лучший медианный RPS среди проверенных уровней для каждой базы и режима.
- `throughput.png` / `.svg`: RPS по количеству клиентов; полоса показывает min/max повторов.
- `latency_p99.png` / `.svg`: p99 по количеству клиентов.
- `best_rps.png` / `.svg`: лучший медианный RPS с диапазоном min/max.
- `memory.png` / `.svg`: расход RAM каждой БД по числу клиентов: среднее и наблюдаемый пик.
- `report.html`: графики, таблицы, версии и ссылки на исходные данные.
- `logs/`: stdout тестов и стартовые/ошибочные логи серверов.
  `DATABASE-MODE-CLIENTS-memory.jsonl` сохраняет исходные отсчёты памяти с временем в наносекундах.

В Docker-прогонах RAM автоматически измеряется для всех шести баз через локальный
Docker Engine API, без вспомогательного процесса в серверном контейнере. Нужен
Docker-контекст с `unix://` socket (обычный Docker Engine на Linux или Docker Desktop
на macOS); удалённые TCP/SSH-контексты пока не поддерживаются. После обновления
стенда один раз запустите `bash tests/comparison/run.sh --build`, чтобы клиент
содержал временные границы измерений.

Метрика — **working set серверного контейнера**, в байтах:
`memory_stats.usage - inactive_file` на cgroup v2 или
`memory_stats.usage - total_inactive_file` на v1, как в
[Docker stats](https://docs.docker.com/reference/cli/docker/container/stats/).
Это память всего сервера, включая аллокатор, соединения и учтённую ядром память,
а не RSS одного процесса, объём полезных ключей или память клиента.

Опрос выполняется каждые 100 мс. В каждый повтор попадают только отсчёты внутри
того же окна, что используется для RPS: подготовка, заполнение, прогрев и дочитывание
после дедлайна исключены. Часы клиента и API принадлежат одному Docker-хосту.
В `raw.jsonl` / `raw.csv` сохраняются `ram_avg_bytes` (среднее отсчётов),
`ram_peak_bytes` (максимум отсчётов), `ram_samples`, `ram_sample_interval_ms`,
`ram_metric`, `started_unix_ns` и `finished_unix_ns`. В HTML и графиках — MiB.
Пик выборочный: всплески короче интервала опроса могут быть пропущены. При задержках
API отсчётов может быть меньше; если в окно не попало ни одного отсчёта или сбор
завершился ошибкой, прогон помечается неуспешным, а не подставляет нули.

Сервер остаётся запущенным между режимами и уровнями нагрузки: удержанная ранее
память аллокатора входит в результат. Замер характеризует указанный набор данных;
для оценки памяти большого хранилища увеличьте `--keys` и `--value-bytes`.
Старые отчёты и частичные `--update` поддерживаются: RAM отсутствующих замеров
показывается как «нет данных», а не ноль. Методика хранится отдельно у каждой БД
в `metadata.json` → `databases` → `memory_measurement`.
Прямой `cargo test` по адресу внешней БД и локальный `run-local.sh` RAM не собирают:
автоматический сбор выполняет Docker-стенд `run.sh` / `run.py`.

RPS = число полностью полученных и побайтно проверенных ответов **внутри окна** /
длительность окна. Подготовка, соединения и прогрев не входят в замер. Запросы,
которые завершились после окна, дочитываются и попадают только в `drained`.
Таймаут запроса — 5 секунд; ошибка проверки или таймаут делают тест неуспешным.

Задержка включает запись запроса и чтение/проверку полного ответа со стороны
клиента. Все успешные ответы внутри окна учитываются в гистограмме. Перцентили
округляются вверх до границы корзины: 32 поддиапазона на степень двойки
в микросекундах, ширина корзины около 3.125% или минимум 1 мкс. На графике —
медиана перцентилей отдельных повторов, а не перцентиль объединённой выборки.

Сравнение характеризует указанный TCP-сценарий в Docker Desktop на этом
компьютере. Лучший проверенный RPS не является абсолютным пределом сервера:
клиент, протокол, квоты CPU и окно замера влияют на результат. Набор из 1024
ключей хорошо помещается в кеши CPU; для оценки реальной рабочей нагрузки
увеличьте набор данных и длительность, отдельно проверьте pipeline и задержки.
Результаты не сопоставляются напрямую с прежними замерами, где Avalanche и
клиенты работали в одном процессе macOS.

## Запуск отдельного Rust-теста

При наличии доступного адреса тестовой базы:

```sh
BENCH_ADDR=127.0.0.1:6379 \
cargo test --release --manifest-path tests/comparison/Cargo.toml \
  --test redis -- --ignored --nocapture --test-threads=1
```

Имена test targets: `avalanche`, `redis`, `valkey`, `memcached`, `dragonfly`, `keydb`.
Фильтр после имени target позволяет выбрать `get_rps`, `set_rps` или `mixed_rps`.
Переменные `BENCH_TEST_CLIENTS`, `BENCH_TEST_SECONDS`, `BENCH_TEST_WARMUP_SECONDS`,
`BENCH_TEST_REPEATS` переопределяют параметры отдельного Rust-теста.

Проверка пакета без внешних баз:

```sh
cargo test --manifest-path tests/comparison/Cargo.toml
python3 -m unittest discover -s tests/comparison -p 'test_*.py'
```

Нагрузочные тесты помечены `ignore`. Обычные тесты приложения запускаются
по-прежнему командой `cargo test` из корня репозитория.

Документация протоколов:
[RESP](https://redis.io/docs/latest/develop/reference/protocol-spec/),
[Memcached basic text](https://docs.memcached.org/protocols/basic/).
